# Find papers

Use this skill to show research papers returned by selected sources. Keep each source's result order; do not judge which tool is better or save items to Zotero. The tested routes are **Codex native web search, Scite, Consensus, Semantic Scholar, Google Scholar, Google Scholar Labs, Scopus AI, PubMed, and UniProt literature**. Read [tested search routes](references/search-tools.md) for source-specific controls, metadata fields, and limits.

## Before searching

In local Codex desktop, show the bundled [search form](assets/search-form.html) in a **visible right-side Codex browser tab** before opening any search results. Use `python3` if it is available; otherwise call `load_workspace_dependencies` and use the Python executable it returns. Run that interpreter on `scripts/intake.py --output <unique temporary JSON path>` from this skill's directory; the script uses only Python's standard library and prints a one-use `http://127.0.0.1` URL. Do not require the student to install Python. If neither interpreter is available, use the chat fallback below and say the checkbox form could not run.

Open the printed URL in `@Browser` and retain the form tab binding. Get the selected in-app browser binding with `agent.browsers.get(id)` using its id from the browser inventory, set its `visibility` capability to `true`, and check that `get()` returns `true`. If it stays `false`, ask the user to show this Codex task and wait; do not ask them to fill an invisible form. After the user submits, read the JSON file and remove it, then call `await formTab.close()` on that same tab before opening any search page. Verify the form tab is gone from the browser tab list. The server exits after submission. Do not ask the user to confirm the submitted search choices or reopen the form during this search; take later corrections in chat. Prefill any topic, context, tools, tab mode, **result mode**, paper limit, or Zotero exclusion choice already supplied in the prompt using the script's matching command-line flags. The user may change those choices in the form. If all inputs were supplied and the user explicitly asks to start without the form, proceed directly.

The form requires a **topic of interest**, accepts an **optional explanation** for context and filters, has independent **checkboxes** for the tested sources above, and lets the user choose visible or background search tabs, a maximum number of papers, and a **results view**: `compare` (default, separate lists by source) or `ranked` (one deduplicated combined list). UniProt searches publications linked to protein records; it is not a general literature index. The Zotero indicator stays neutral until the user ticks **Only show papers not in Zotero**; then it checks whether the local API can reach My Library. Do not scan My Library or request per-paper Zotero status when that box is unticked. Submission starts the search without a review step. Use the submitted values exactly, except that a later user correction overrides them. The maximum applies per source; the combined view has the same final maximum. With Zotero exclusion on, each source's target becomes greater than that maximum after exclusion. If a local form cannot be opened, ask for missing inputs in chat and clearly say that this fallback has no checkbox UI.

Default source selections are **Google Scholar, PubMed, and Semantic Scholar**. Prefill different selections when the user specifies them. Treat all submitted source checkboxes as independent selections. Apply later chat corrections immediately: adding a source extends the active list; an explicit replacement changes it. Before searching and before final output, check the active list against the submitted choices plus those corrections so no selected source is silently dropped. Do not reopen the form or ask for confirmation.

**The tab mode selects the discovery route.** In **visible** mode, search every selected scholarly website through its browser UI, including sources with working APIs. Call `await (await browser.capabilities.get("visibility")).set(true)` and verify `get()` returns `true` before searching. Open search, detail, and verification pages with `cua.createBrowserTab("iab", url, { visible: true })` and verify they appear in Codex's right-side preview. Preserve the website's result order and use its pagination. If the task is hidden or visibility stays false, tell the user and wait before browser searches.

In **background** mode, try official APIs or provider MCP tools first; use browser fallback with `{ visible: false }` when needed. Metadata APIs may fill missing DOI, author, or summary evidence in either mode without replacing the discovery route or changing its rank. The intake form is always visible. **Codex research** uses its native web search in either mode because it has no browser search UI; any verification pages follow the selected tab mode.

## Search

Make a focused question and a few keyword variants from the submitted topic and optional explanation. Extract the explanation's constraints before searching: publication dates, study types, populations or species, methods, and exclusions. Apply explicit constraints as filters before ranking and before the max-paper cutoff; use source filters to narrow discovery where available, then verify each candidate's metadata against the constraints. For example, **published after 2016** means publication year 2017 or later. If "new", a term, or an acronym has multiple plausible meanings that would materially change the search or ranking, ask one focused question in chat; do not reopen the form. If the explanation resolves it, proceed.

### Run sources concurrently

If Zotero exclusion was selected, finish its snapshot before dispatching searches. Otherwise, begin without contacting Zotero. Keep a separate ledger, pagination cursor, eligible count, and running-job handle for each selected source.

**Dispatch every selected source's first search batch before starting DOI or summary enrichment.** In visible mode, start searches in separate visible preview tabs, serializing foreground input and navigation; use independent tab-scoped reads while other tabs load. In background mode, group independent API or provider MCP calls with `Promise.allSettled` where the tools permit it, and inspect every result. For shell API helpers, use a short command yield (about 1000 ms), retain returned process session IDs, and work on browser fallbacks while those processes run. Opening tabs together is only setup; the searches and result retrieval must also overlap where supported.

As batches finish, screen them and dispatch that source's next eligible batch. Advance other ready sources during a source's loading, rate-limit backoff, or login wait. Each source stops at its own target or documented limit. Use tab-scoped browser reads; serialize foreground navigation in visible mode. If a browser backend cannot isolate concurrent tab operations, serialize those operations while independent API jobs continue. Respect tools that forbid concurrent calls, including Codex's hosted web search.

Schedule DOI and content enrichment separately from discovery. Give ready discovery batches priority over slow publisher checks, and run independent content requests concurrently where provider limits permit. Use one sequential DOI resolver with a shared cache, starting it after any running PubMed helper finishes; UniProt, other provider searches, and browser work can continue while it runs. One source's failure or metadata wait must not stop the others.

### Retrieve and screen results

For **visible mode**, use the selected source's documented website controls and rendered result cards. Search and paginate in the preview; do not substitute API discovery even when it would be faster. Reuse captured metadata before enriching missing fields.

For **background mode**, try each source's available official API or provider MCP search tool first. Discover the relevant tool and read its current schema before calling it. Follow documented pagination and metadata-fetch requirements. Use browser fallback when no supported API is available, access fails after its documented retry/backoff, or the API cannot supply a needed field, filter, or additional results. Record the fallback reason internally. Do not invent endpoints, substitute unofficial scraping services, or treat an API's empty result set as an access failure. Preserve the route's returned order; a different website ranking alone is not a reason to abandon a working API.

Collect structured records with stable paper ID/URL, title, authors, year, journal, summary or abstract, source rank, and DOI/PMID. Process small batches with the [candidate ledger](references/candidate-ledger.md). Resolve missing DOIs through [metadata lookup](references/metadata-lookup.md) even when Zotero exclusion is off. Keep the discovery source and rank when enriching metadata. A DOI explicitly attached to that paper in official metadata or a source record is verified; a guessed DOI is not.

For visible discovery or background browser fallback, use Codex's built-in browser in the chosen tab mode. Extract structured arrays from rendered result cards with tab-scoped CDP `Runtime.evaluate`. Follow **Next**, numbered pages, or **Load more** until the source target or an access limit is reached. Open individual source or publisher pages only for facts unresolved by captured metadata and API enrichment. The tested Scholar page-2 recovery is in the source reference. Never inspect private site state or session tokens.

For **PubMed and UniProt**, use their documented website search and pagination in visible mode. In background mode, call the official public API helper in [metadata lookup](references/metadata-lookup.md) directly: PubMed uses ESearch plus batch EFetch; UniProt uses **Literature citations**. Both return titles, authors, years, DOIs, and author abstracts when available. Preserve API order, screen the user's filters, and follow `next_start` or `next_url` until the source target is reached. Neither API route requires an account, API key, or preliminary browser visit. In either mode, metadata enrichment must retain the original discovery IDs and ranks. Use UniProt protein records only to find their linked publications when the question requires it.

For **Codex research**, use the available first-party web search tool iteratively: search the question, refine with terms from promising results, and screen title/snippet/DOI leads in small batches. It is a Codex web search workflow, not the separate Deep research feature in ChatGPT Work. Hosted web-search calls appear in the task transcript; the visible/background choice controls browser tabs opened to inspect a needed paper fact, not the web-search calls themselves. If web search is unavailable, mark that source unavailable and continue.

If **Consensus** browser search blocks the selected search or needed paper details with a sign-in gate, show its sign-in flow in a **visible Codex browser tab**, even when background search was selected. Set the in-app browser's `visibility` capability to `true` and verify it; if a hidden Consensus tab triggered the gate, open the original Consensus search page with `{ visible: true }` in a new tab and follow its sign-in control. Do not copy an authentication redirect URL or switch to the user's regular browser. Ask in chat with two clear choices: **Sign in to Consensus** in that tab and tell Codex when finished, or **Skip Consensus**. Pause Consensus and leave its tab available while other independent sources continue; wait for the user's choice before resuming or skipping Consensus, and do not enter credentials or assume that waiting means skip. After the user signs in, verify that Consensus results or paper details are accessible before resuming. If background mode was selected, close the temporary visible sign-in tab and continue Consensus search in background; in visible mode, continue in the visible tab. If the user skips, close only agent-created Consensus tabs, continue with the other selected sources, and report Consensus as skipped. If it was the only source, ask for another source in chat without reopening the intake form. Do not interrupt for a sign-in button alone when the required anonymous results are accessible.

For **Google Scholar Labs** browser search, open `https://scholar.google.com/scholar_labs/search` in Codex's browser and enter an English research question. If it redirects to Google sign-in, leave a **visible Codex preview tab** for the user to sign in or choose to skip Labs; never enter credentials or copy the authentication redirect. Continue other selected sources while waiting. After sign-in, verify that the question box or result cards are accessible and return to the selected tab mode; if the user skips or the account has no Labs access, close only agent-created Labs tabs, mark the source unavailable, and continue. Use the rendered Scholar Labs cards and **More results** button as documented in [tested search routes](references/search-tools.md). Treat its generated explanations as AI takeaways, not author abstracts. Labs and ordinary Google Scholar are separate selected sources even when they surface the same paper.

For `N = max_papers`, independently collect up to **N distinct papers matching the user's explicit topic and filters from each source**, whether or not its card shows a DOI. With **only_not_in_zotero** on, instead continue each source until it has **more than N distinct papers confirmed `not_found` in the pre-search My Library snapshot** (minimum `N + 1`); title matches without DOIs may be confirmed `in_zotero` and excluded. Do not count duplicate hits, possible Zotero matches, or papers without a verified DOI as absent. Check each small batch and its ledger count before loading more. Do not divide the target among sources or stop because another source has enough papers. If a source cannot reach its target, show its actual results and a brief access-limit reason. Use Google Scholar and Scholar Labs interactively, without bulk retrieval or a page-crawling loop.

Only when Zotero exclusion is selected: review an early title match against first author, year, and journal. The snapshot stores those Zotero fields; the ledger returns a precise reason for missing or conflicting fields. A fully corroborated title match is `in_zotero` even without a DOI. Resolve a `possible_match` from source metadata when practical; otherwise keep it out of the absent count. Resolve missing DOIs for the remaining eligible papers before claiming absence. With exclusion off, perform DOI lookup without contacting Zotero. In either case, use **one global sequential DOI lookup queue** and a shared temporary cache; never fan out Crossref queries. Compare title, year, and first author before accepting title-search metadata. DOI enrichment must preserve the original discovery source, URL, and rank.

For `ranked` mode (the optional **Combined list** view), pool the source results, deduplicate verified DOIs and clear title/year/author matches, then show up to N papers that meet the user's stated filters. Preserve every source name for a paper. Use the paper-summary guidance below; do not invent a tool-quality judgment or open publisher pages for every row.

For `compare` mode (the default **Results by source** view), keep each tool's own result order and use [compare_results.py](scripts/compare_results.py) on the source ledgers. Follow [compare-tools output](references/compare-tools.md): show each selected tool's returned papers separately, including repeated papers across tools. Do not add a scorecard, search-process notes, or an assessment of which tool is better.

## Paper summaries

For **UniProt literature results**, start the Summary with one sentence naming the relevant protein, its organism, and its documented function. Then summarize the paper's scope, approach, and findings or conclusions. Verify the function from the linked UniProt protein record or supported paper content, matching the protein and organism. For papers covering several proteins, describe the main relevant ones compactly. Keep the known protein function distinct from what this paper establishes; if the function cannot be verified, state that briefly rather than guessing. See [UniProt metadata](references/metadata-lookup.md#uniprot-literature).

Write **an informative, compact paragraph in your own words explaining what each paper is about**, usually two or three sentences (about 35–65 words when sufficient content is available). Describe its question or scope, the specific features or mechanisms it examines, and the connections or conclusions it discusses. Name relevant genes, pathways, methods, populations, or species when the evidence supports them, rather than merely restating the title. If the user supplied context or a particular research focus, foreground those supported aspects; otherwise describe the overall scope. For a review, explain what it synthesizes and the biological or practical implications it discusses; for an original study, explain the approach and main result when available. Use paper content, author abstracts, and reliable source descriptions as evidence. Keep the description objective, without praise or an invented relevance judgment; use a shorter description when the evidence is limited.

An abstract is evidence for the summary, not text to copy into the results. Keep the evidence type internally as `summary_basis` and the finished description as `paper_summary`. Do not prefix ordinary summaries with **Abstract:** or **Snippet:**. If the available information cannot support a useful description, try official metadata first, then source details only for the missing information. When only a verified title or indexing terms are available, describe that limited scope and mark **Title/indexing only**; do not leave a cell as **Abstract unavailable** or invent methods or findings. Mark **AI summary only** when an AI-generated takeaway is the sole substantive evidence. A reference list or a snippet quoting another paper does not establish this paper's findings.

## Optional Zotero exclusion

Only if **Only show papers not in Zotero** was selected, read Zotero **My Library** once before any source search using [zotero_check.py](scripts/zotero_check.py) with `--snapshot <unique temporary JSON path>`. This scans non-attachment items and saves a private DOI/title/metadata index. For each source's small batch, run [screen_batch.py](scripts/screen_batch.py) with the snapshot, a separate ledger, `--max-papers N`, and `--only-not-in-zotero`; see [candidate ledger](references/candidate-ledger.md). Read `count_toward_target`, `needs_doi`, and title matches needing review before continuing. Reuse the snapshot, then delete temporary batches, ledgers, and snapshot at the end. The scope is My Library, not group libraries. Do not use Zotero quick search by DOI as proof of absence.

If the selected exclusion scan fails, ask the user to make Zotero accessible or drop that filter; do not claim absence. If exclusion is **off**, never call `zotero_check.py` or create a snapshot. Run [screen_batch.py](scripts/screen_batch.py) **without `--snapshot` or `--only-not-in-zotero`** to keep source ledgers; its `unchecked` status is internal and should not appear as a per-paper claim. The form's neutral indicator makes no Zotero request while exclusion is off.

Use **three columns** in either view: **Paper**, **Summary**, and **Source** (or **Source · Zotero** only when exclusion is on). Put the linked title, authors, and year together in Paper. Link the title to `https://doi.org/<DOI>` whenever a DOI is verified, including through official metadata lookup. Do not finish with a missing-DOI label merely because a result card omitted it. After the documented lookup and needed source-detail check, keep a genuinely unresolved paper linked to its source and give a short factual reason, such as **DOI lookup blocked**, **DOI records conflict**, or **DOI unavailable**. Use the paper-summary guidance above for Summary. The third column lists the discovery source(s) and source rank, not the metadata lookup provider. When exclusion is on, add **Not found in Zotero (My Library)** for every displayed paper; never report that status without the snapshot. Show only the result tables, plus one brief sentence if a selected source is unavailable or returns fewer than requested. Do not print query/page counts, coverage breakdowns, search notes, or a judgment about tool quality.
